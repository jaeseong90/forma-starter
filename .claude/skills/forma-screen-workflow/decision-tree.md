# 방식 A/B 판정 트리

FORMA 화면 요구를 받았을 때 YAML 1장(방식 A)으로 갈지, 커스텀 4파일(방식 B)로 갈지 기계적으로 판정한다.

## 판정 규칙

**모두 true면 방식 A, 하나라도 false면 방식 B.**

| # | 조건 | True 판정 |
|---|------|-----------|
| 1 | 관련 테이블이 1~2개 (마스터 1 + 디테일 1까지)? | Y |
| 2 | 저장 시 한 번에 쓰는 테이블이 2개 이하? | Y |
| 3 | 검색 조건이 LIKE / Equal / dateRange 조합으로 표현됨? | Y |
| 4 | 자동 계산(금액·수량 수식)이 없음? | Y |
| 5 | 상태 전이(DRAFT→APPROVED 등)가 없음? | Y |
| 6 | 자동 채번이 `SeqGenerator.next()` 없이 DB DEFAULT나 사용자 입력으로 충분? | Y |
| 7 | 외부 API 호출(Claude·Gemini·결재 시스템 등)이 없음? | Y |
| 8 | 파일 업로드/다운로드가 없음? | Y |
| 9 | 권한이 버튼 단위(조회/신규/저장/삭제)로 충분하고 필드 단위 readonly가 없음? | Y |
| 10 | 트랜잭션 내 순서 의존(A 저장 실패 시 B 롤백) 관계가 없음? | Y |

## 판정 결과

- **모두 Y** → 방식 A. `/new-screen` 실행.
- **9개 Y, 1개 N**이고 그 N이 쉽게 우회되면 (예: 외부 API 없이도 MVP로 충분) 사용자에게 확인: "이 기능은 MVP에서 빼도 될까요?" 수용되면 방식 A.
- **2개 이상 N** → 방식 B. `/yaml-to-code` 또는 직접 작성.

## 경계 샘플

### 방식 A로 충분한 예
- 부서관리, 역할관리, 코드관리 같은 마스터 데이터
- 단순 로그 조회 (읽기 전용 리스트)
- 단일 테이블 + 1개 디테일 테이블의 CRUD (예: 거래처-담당자, 영업기회-마일스톤 스켈레톤)

### 방식 B 필요 예
- 회의록 (음성→AI 요약, 파일 업로드) → 7·8 실패
- 결재 (상태 전이 + 결재선) → 2·5 실패
- 견적·계약 (자동 계산, 승인 흐름) → 4·5 실패
- 대시보드 (여러 테이블 집계 + 차트) → 1·3 실패

## 판정 후 AI 행동

- 판정 근거를 사용자에게 간단히 알린다: "이 화면은 방식 A로 갑니다 — 단일 테이블 CRUD만 필요해서."
- 판정을 뒤집어야 한다고 사용자가 지시하면 따른다. 그러나 자의적으로 뒤집지 않는다.
- 방식 A 경로 중 요구가 확장되면(사용자가 "계산 기능도 추가해줘" 추가) 즉시 재판정하고 방식 B 승격 제안.
